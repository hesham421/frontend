# Generate Frontend Module Execution Setup

> **v2.1 NEW FILE — lives in `frontend/governance/.claude/commands/`, NOT**
> **backend/.** This is the frontend-native counterpart to
> `backend/governance/.claude/commands/generate-module-setup.md`. It exists
> because Playwright/frontend execution is frontend's own governance
> responsibility (WORKSPACE-ARCHITECTURE-REFERENCE.md Section 11.3) — it
> should never be driven by reaching into a sibling backend repo.
>
> **v1 modules (ORG, NOTIFICATION, FILESVC) do NOT use this file.** Their
> PLAYWRIGHT content is still generated by backend's `generate-module-setup.md`
> per the original STRUCTURAL LAW asymmetry — that is a deliberate, unchanged
> design decision, not an oversight (see `frontend/governance/README.md`'s
> "PLAYWRIGHT re-verification" section). This file applies ONLY to v2 modules.

## Your Task

Scan THIS repo (frontend/governance/) for the specified module and generate
three files, entirely within this repo:
1. `.claude/commands/execute-frontend.md` — implementation phase execution
   (F1, F2, F3, F4, SEC-FE, ALIGN-FE)
2. `.claude/commands/execute-frontend-test.md` — frontend test phase execution
   (frontend-test / Playwright), gated on execute-frontend.md's phases
3. `governance/modules/[MODULE]/execution-state.json` (this repo's own copy —
   frontend-scoped only; does NOT merge with or overwrite backend's own
   execution-state.json for the same module, which stays backend-scoped)

Both generated commands reference `TEST-EXECUTION-AGENT.md` for MCP
boundaries and the failure taxonomy — same shared file convention as
backend's version (a frontend-local copy of that file, not a cross-repo read).

## Step 1 — Scan THIS repo's structure (frontend repo only — no backend reach)

```bash
# Frontend execution phases + frontend test scenarios — this repo only.
# No ../backend/... path anywhere in this scan or in anything it generates.
find governance/modules/$ARGUMENTS/packages/frontend-execution -type f -name "*.md" | sort
find governance/modules/$ARGUMENTS/packages/frontend-test -type f -name "*.md" | sort
```

From the scan results:
- Identify all PHASES (top-level folders under `packages/frontend-execution/`)
- For each PHASE, identify all SUBs (files inside the phase folder, excluding `index.md`)
- Preserve the exact order from the filesystem sort
- For each SUB file, read the first 40 lines and count the number of tasks

Expected phases (in strict execution order — v2 frontend):
`F1 → F2 → F3 → F4 → SEC-FE → ALIGN-FE`

Only include phases that actually exist in the scanned structure. If F1-F4
are all missing, that means Step 0's precondition check should have already
stopped you — do not proceed with an empty phase list.

**Test phase (single TEST-PHASE, no MARK split — same v2.0 simplification
as backend-test):**

`packages/frontend-test/` is the Playwright boundary itself (no
JUNIT/PLAYWRIGHT subfolder distinction needed — see
`PROJECT-3-REGISTRY.md` Section 5.7.4). Treat it as ONE TEST-PHASE named

## Step 2 — Generate `execution-state.json` (this repo's own copy)

Create the file at: `governance/modules/$ARGUMENTS/execution-state.json`
(this repo's copy — frontend-scoped only; backend's own copy of this
filename, in `backend/governance/modules/$ARGUMENTS/`, is a DIFFERENT file
tracking backend phases — the two are never merged or synchronized
automatically)

```json
{
  "module": "[MODULE]",
  "governance_model": "v2",
  "scope": "frontend",
  "generated_at": "[today's date]",
  "backend_module_complete_confirmed": true,
  "ui_shell_complete_confirmed": true,
  "current_phase": "[FIRST_PHASE]",
  "current_sub": "[FIRST_SUB or null]",
  "api_docs_path": "../backend/governance/modules/[MODULE]/api-docs/",
  "phases": [
    {
      "id": "[PHASE_NAME]",
      "status": "PENDING",
      "subs": [
        { "id": "[SUB_NAME]", "status": "PENDING" }
      ]
    }
  ],
  "test_phases": [
    {
      "id": "frontend-test",
      "status": "PENDING",
      "gated_by_phases": ["F1", "F2", "F3", "F4", "SEC-FE", "ALIGN-FE"],
      "header_file": "packages/frontend-test/UI-FLOWS-HEADER.md",
      "mandatory_file": "packages/frontend-test/MANDATORY-P.md",
      "subs": [
        { "id": "UI-FLOWS", "status": "PENDING" },
        { "id": "INT-FLOW", "status": "PENDING" }
      ]
    }
  ],
  "blocked": [],
  "deferred_xm": [],
  "api_doc_gaps": []
}
```

Note the two boolean confirmation fields (`backend_module_complete_confirmed`,
`ui_shell_complete_confirmed`) — these record that Step 0's gate actually
passed, so a later session re-reading this state file doesn't have to
re-derive that fact from scratch (but does NOT replace re-checking the
live gate status if genuinely re-verifying — this is a record, not a cache
to trust blindly across a long time gap).

`api_doc_gaps[]` entries use the identical format backend's version uses —
see `backend/governance/.claude/commands/generate-module-setup.md` Step 2
for the schema (not repeated here to avoid drift between two copies).

## Step 3 — Generate `.claude/commands/execute-frontend.md`

Create the file at: `.claude/commands/execute-frontend.md`

Same STEP 0 (context safety assessment) → STEP 1 (execution) → STEP 2
(session report) shape as backend's `execute.md` — see that file for the
exact assessment/chunking table and report format (identical logic, just
applied to this repo's `phases[]`). Generate with these frontend-specific
adjustments:

### Per sub (STEP 1, adjusted for frontend):

1. Read sub file completely:
   `governance/modules/[MODULE]/packages/frontend-execution/[PHASE]/[SUB].md`
   (if no sub → `[PHASE]/index.md`)
2. Identify all tasks in the sub
2.5. **UI Shell reference check (ALL frontend phases, not just F1)** — before
   writing any task's code, confirm whether a corresponding component/route
   already exists in the UI Shell (implemented earlier, before this command
   ever ran — see `GATE: UI SHELL COMPLETE` in Step 0). If it exists: this
   phase CONFIRMS/INTEGRATES with it — modify the existing file, do not
   create a competing new one. If a task calls for something genuinely
   absent from the Shell: flag it clearly in the session report as a Shell
   gap, implement it as an explicit addition, and note it — do not silently
   assume the Shell already covers everything F1-F4 lists.
3. **API Contract Resolution** (F1/F2/F3 only, same priority order as
   backend's STEP 1.5 — api-docs first, backend source only if genuinely
   missing from api-docs, see backend's `execute.md` for the full protocol;
   `api_docs_path` in this repo's `execution-state.json` points across to
   `../backend/governance/modules/[MODULE]/api-docs/`)
4. Map each task to the skill routing table in `frontend/governance/GOVERNANCE-RULES.md`
5. Read required skills from `.github/skills/frontend/`
6. Execute all tasks in order
7. Run `validate-frontend-feature` after last task
8. Mark sub as COMPLETE in this repo's `execution-state.json`

### Blocked items — OQ / XM DEFERRED

- OQ-blocked task → skip, add to `blocked[]`
  Mark in code: `// TODO: OQ-[ID] — pending resolution`
- XM DEFERRED → **this should essentially never occur in frontend code** —
  XM-IDs are exclusively a backend concern (CORE-5 RULE-6, this ecosystem's
  own rule). If you find yourself about to write an XM-related TODO in
  frontend code, stop — that's a sign a backend concept leaked into a
  frontend task incorrectly; flag it instead of implementing it.
- Continue remaining tasks — never stop the phase for a blocked item

### Exit — after all subs in phase complete

Same as backend's version — mark phase COMPLETE, advance `current_phase`,
print the same-shaped execution report (see backend's `CLAUDE.md` Phase
Execution Protocol for the exact report template).

## Step 3B — Generate `.claude/commands/execute-frontend-test.md`

Create the file at: `.claude/commands/execute-frontend-test.md`

Mirrors backend's `execute-test.md` structure exactly (STEP 0 gate check →
STEP 1 execution → STEP 2 report), applied to `test_phases` (which has
exactly one entry, `frontend-test`) instead of JUNIT/backend-test. All
paths resolve within THIS repo only:

```
frontend-test → governance/modules/[MODULE]/packages/frontend-test/[FILE]
```

Test generation: POM + spec file per scenario, following
`TEST-EXECUTION-AGENT.md`'s NEW-mode conventions (Page Object Model,
`data-testid` first, no `waitForTimeout`). Run via `playwright-mcp`, per
the shared MCP execution order (oracle-sql precondition → playwright-mcp
execute → oracle-sql confirm → screenshot on failure) — `oracle-sql` MCP
here still reaches the real database for precondition/confirmation
checks, same as backend's JUnit tests do; that's a data-layer concern,
not a repo-boundary one.

Session report: same shape as backend's TEST-REPORT template, written to
`reports/TEST-REPORT-[MODULE]-frontend-[YYYY-MM-DD].md`. Any `FAIL` →
hand off to `AUTONOMOUS-FULLSTACK-FIXING-AGENT.md`, same as backend.

## Constraints (NON-NEGOTIABLE)

- NEVER run this command for a v1 module — use backend's
  `generate-module-setup.md` for ORG/NOTIFICATION/FILESVC instead
- NEVER skip Step 0's precondition gate — all four checks are mandatory,
  not advisory
- NEVER reach into `../backend/governance/modules/[MODULE]/packages/` for
  execution or test content — this repo's own `packages/frontend-execution/`
  and `packages/frontend-test/` are the only sources
- The ONLY two sanctioned cross-repo reads in this file are:
  (1) reading `../backend/governance/governance-tools/modules-registry.json`
      in Step 0, to determine governance_model (this repo does not
      maintain its own copy — modules-registry.json is backend-owned
      by design)
  (2) reading api_docs_path (`../backend/governance/modules/[MODULE]/api-docs/`),
      since real API Docs are inherently backend-generated
  No other `../backend/...` path may appear anywhere else in this file.
- NEVER redesign a component/route that already exists in the UI Shell —
  confirm/integrate per Step 3's "UI Shell reference check"
- NEVER invent an XM-ID reference in frontend code
- ALWAYS update this repo's own `execution-state.json` after every sub —
  never write to or read from backend's copy of that filename
